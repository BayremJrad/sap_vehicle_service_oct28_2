# Vehicle Service API – Business Requirements

## 1. Purpose

Provide an API to manage a catalog of vehicles so that client applications can register, view, update, and remove vehicle records.

## 2. Scope

**In scope:** Create, Read (list and single), Update, and Delete of vehicle records.

**Out of scope:** Authentication/authorization, service/maintenance history, ownership, search/filtering, pagination.

## 3. Vehicle Data

| Field      | Type    | Required | Notes                                   |
|------------|---------|----------|-----------------------------------------|
| `id`       | integer | System   | Generated by the service, read-only     |
| `vin`      | string  | Yes      | Must be unique across all vehicles      |
| `make`     | string  | Yes      | e.g. Mercury                            |
| `model`    | string  | Yes      | e.g. Villager                           |
| `year`     | string  | Yes      | e.g. "1994"                             |
| `nickName` | string  | No       | Friendly name, e.g. "The Lisa Marie"    |
| `miles`    | integer | No       | Current odometer reading                |

## 4. Business Requirements

| ID    | Requirement |
|-------|-------------|
| BR-1  | Users can create a vehicle by providing its details. The service assigns a unique `id` and returns the created record. |
| BR-2  | A vehicle cannot be created if its VIN already exists. The response identifies the existing vehicle. |
| BR-3  | A vehicle cannot be created if a required attribute is missing. The response names the missing attribute. |
| BR-4  | Users can retrieve the full list of vehicles. |
| BR-5  | Users can retrieve a single vehicle by `id`. |
| BR-6  | Users receive a clear "not found" message when the requested `id` does not exist. |
| BR-7  | Users can partially update a vehicle (e.g. update only `miles`) and receive the updated record. |
| BR-8  | Updates with an invalid request body are rejected with a clear message. |
| BR-9  | Users can delete a vehicle by `id`. |
| BR-10 | Unexpected failures return a generic error message without exposing internal details. |

## 5. Operations Summary

| Operation | Method & Path          | Success | Error responses |
|-----------|------------------------|---------|-----------------|
| Create    | `POST /vehicles`       | 201     | 400, 409, 500   |
| List      | `GET /vehicles`        | 200     | 500             |
| Retrieve  | `GET /vehicles/{id}`   | 200     | 404, 500        |
| Update    | `PATCH /vehicles/{id}` | 200     | 400, 500        |
| Delete    | `DELETE /vehicles/{id}`| 204     | 500             |

Error responses use the shape `{ "message": "<description>" }`.

## 6. Acceptance Criteria

- **Create:** Given a valid payload with a new VIN, the service returns `201` with the vehicle and its new `id`.
- **Duplicate VIN:** Given a VIN that already exists, the service returns `409` and the existing vehicle's `id`.
- **Missing field:** Given a payload without a required field, the service returns `400` naming that field.
- **List:** The service returns `200` with an array of vehicles (empty array if none).
- **Retrieve:** Given an existing `id`, the service returns `200` with that vehicle; otherwise `404`.
- **Update:** Given an existing `id` and valid partial payload, the service returns `200` with the updated vehicle; an invalid body returns `400`.
- **Delete:** Given an `id`, the service returns `204` with no body.

## 7. Open Questions

- Should updating to a VIN that belongs to another vehicle be rejected (`409`)?
- Should `PATCH`/`DELETE` on a non-existent `id` return `404`? (The current contract only defines this for `GET`.)
- Should `year` and `miles` be stored as numbers? The contract currently mixes types (`miles` is an integer in requests but a string in the create example response).
